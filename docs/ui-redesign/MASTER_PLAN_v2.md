# VELARIS — MASTER UI/UX REDESIGN PLAN FOR CODEX

**Версия:** 2.0 — согласованный мастер-план, 09.11.2026\
**Статус:** продуктовые решения утверждены владельцем; код по этому плану пока не менялся.\
**Объект:** нативное Android-приложение Velaris, в первую очередь экраны Compose.\
**Репозиторий:** https://github.com/sufffear/-Kegl\
**Скриншоты:** https://drive.google.com/drive/folders/1QLHeO2giQzebHNlkTJfYgE_2k4QOfL3t\
**Предыдущее исследование:** `Velaris_UI_UX_Audit_v1_Draft.md`; настоящий документ заменяет его рекомендации там, где владелец уже принял решения.

> **Цель:** сделать Velaris просторным, последовательным, отзывчивым и атмосферным: уютное тёмное фэнтези + современный минимализм. Функции не исчезают при упрощении UI. История тренировок, статистика, игровое состояние, монеты, предметы, сюжет, настройки API, резервные копии и звук при заблокированном экране должны сохраниться.
>
> **Граница:** это ТЗ для будущего последовательного выполнения Codex, а не разрешение массово переписывать приложение одним коммитом. Начать с проверки текущего checkout и сохранности данных. Каждая стадия — отдельная маленькая поставка с доказательствами проверки.

## 0. Источник истины и предостережения перед работой

1. Зафиксировать `HEAD`, ветку, статус рабочего дерева, `applicationId`, `versionCode` и доступные Gradle-задачи. **Не перетирать незакоммиченные изменения**. Создать отдельную ветку, например `feat/velaris-ui-cleanup`, только если среда и политика работы позволяют; не публиковать/push без отдельного указания владельца.
2. Сверить установленную на телефоне версию со скриншотами и реальным checkout. В `docs/BUILD_STATUS.md` смешаны описания нескольких итераций (4 вкладки с «Книгой», 3 вкладки без Reader, последующие варианты), а имена/тексты «Модель для историй», Grok/Gemini, «Наши маленькие привычки» могут находиться в сборке/ветке, отличной от исследованной `main`. **Не делать вид, что отсутствующий в checkout экран уже найден**. При расхождении отметить его и найти соответствующий источник прежде, чем изменять.
3. Область первого цикла — нативный Kotlin/Compose (`app/`). В репозитории также есть `src/*.tsx`; браузерную реализацию не обновлять автоматически. Если в установленном APK присутствует функция, отсутствующая в `app/` текущей ветки, остановить только затронутый подэтап и описать расхождение; остальные независимые работы можно продолжить.
4. Не меняем бизнес-правила игры или тренировок ради дизайна. Любая новая видимая цифра берётся из существующего источника статистики, а не рассчитывается альтернативной формулой в Composable.
5. Любое скрытие функции сопровождается проверкой её нового доступного пути. При удалении согласованных **искусственных** UI-взаимодействий не удалять старые сохранения или ключи без отдельной, протестированной задачи на миграцию.
6. Перед первым изменением получить резервный архив приложения и контрольную фиксацию данных. Если ни устройство, ни тестовые данные недоступны, пометить физическую проверку `NOT RUN`, не писать `PASS`.

**Особые риски:**
- Снимок Шанталь сейчас записывается из Compose через `SideEffect { progressRepository.save(progressSnapshot) }`. **Не менять эту схему записи между этапами только ради рефакторинга UI**; сначала сохранить события и проверить нет ли повторного начисления при навигации/пересоздании экрана.
- Резервный архив формата 2 содержит состояние Шанталь, но восстановление нескольких Android-хранилищ не является одной гарантированно атомарной транзакцией. Тестировать на отдельном профиле/копии.
- `docs/BUILD_STATUS.md` упоминает ограничение системного масштабирования шрифта для решения переполнений. При редизайне **не решать проблемы текста насильственным уменьшением fontScale**: исправлять ширину/перенос/вертикальное расположение и проверять увеличенный системный шрифт.
- API-ключи для истории не должны попадать в логи, скриншоты диагностики или архивы, если текущая политика их исключает.

## 1. Неприкосновенные продуктовые решения

### 1.1. Общая структура

**Основная нижняя навигация: ровно четыре раздела** (порядок неизменен):

`Главная` · `Тренировки` · `Шанталь` · `Статистика`

- **Настройки:** через шестерёнку в верхней панели, отдельный маршрут с нормальным `Back`, а не пятая вкладка.
- **Активная тренировка:** самостоятельный режим; при уходе на другой раздел сохраняется компактная панель с фазой/остатком/паузой/возвратом над нижней навигацией, без перекрытия содержимого.
- **Подэкраны:** журнал, конструктор, карта, лавка, интерьер, сумка, история, управление ключом, диагностика и т. п. открываются как дочерние экраны/маршруты; нижняя навигация не обязана дублироваться внутри каждого полноэкранного режима.
- **Навигация назад:** возвращает к предыдущему разделу/экрану и прежней позиции прокрутки; если открыт диалог, сначала закрывает диалог; активную тренировку не останавливает.

### 1.2. Главная

**Первый экран, без обязательной прокрутки:**
1. Небольшая шапка + шестерёнка.
2. Одна **крупная карточка «Активная сессия»**: если уже запущено — вернуться/пауза; иначе — следующий подход и заметная кнопка «Начать».
3. Акцент на следующем периоде дня; два других периода — компактные переключатели/индикаторы (утро/обед/вечер).
4. Компактный **streak / серия дней**, без дублирования нескольких достижений.

**Убрать с главной, переместить в статистику/игровые разделы:** 7-дневные цифры, минуты, количество сессий, недельные графики, тепловые карты, календарь, подробную дневную статистику, жетоны/награды и игровую валюту. Никакие данные не удалять.

**Состояния:** ещё не тренировался; есть следующий период; активная/приостановленная тренировка; все обязательные подходы выполнены; день без заданий; нет данных/ошибка чтения БД. Для каждого — понятное одно главное действие, без `0/0` и ложных наград.

### 1.3. Тренировки

- В начале — **одна компактная карточка текущего дня кампании**, без раскрытия всех этапов на главном экране.
- **«Другие тренировки»** отдельным видимым переходом ниже кампании; внутри свободные интервалы, пресеты и конструктор. Не смешивать их с обязательным днём.
- Утро / обед / вечер: на главной виден следующий период, на экране «Тренировки» можно переключать периоды; подробности упражнений открывать отдельно.
- Не показывать длинные инструкции в каждой карточке; правильная техника/предупреждения доступна через справку.
- **Активный таймер:** крупное время, текущая фаза (удержание/отдых/подготовка/пауза), необходимые кнопки паузы и остановки; доступ к деталям — вторичный. Не менять аудио/вибрацию в фоне и поведение при выключенном экране.
- **После завершения:** короткий наградной экран, факт завершения, одна главная награда/краткий итог и одно понятное действие. Полная аналитика — в журнале.

### 1.4. Шанталь — утверждённые пять решений

- **State-driven главный экран**: один главный CTA в зависимости от состояния персонажа: дома/готова, поход идёт, вернулась с историей, ожидается награда/выбор, нужно завершить текущий сюжетный шаг. Не дублировать одновременно взаимоисключающие CTA.
- **Сбалансированность:** иллюстрация Шанталь занимает ориентировочно **35–45% полезной высоты** на стандартном телефоне; при малом экране/большом шрифте адаптировать, не обрезать кнопки.
- **Иерархия:** имя, стадия/небольшой статус → большая иллюстрация → краткая живая реплика (состояние, а не искусственный бесконечный диалог) → одна главная кнопка → **три быстрых перехода «Сумка», «История», «Интерьер»** → компактная ссылка **«Мир Шанталь»**.
- **«Мир Шанталь»:** карта, магазин, характер/развитие, прочие функции и настройки Шанталь. Полноценные дочерние экраны, не огромный диалог «Книга странствий» на шесть разделов.
- **Подсказки:** текстовые объяснения для сложных механик открываются только по `?` / `i`; очевидные кнопки не сопровождаются обучающими абзацами. Для ошибок/опасных действий информация должна быть доступна сразу.
- **Стиль:** тёмный лес, тёплые акценты, хорошая иллюстрация, минимум рамок и тяжёлых контейнеров. Никакой бессистемной россыпи эмодзи рядом с иконками.

### 1.5. Шанталь — убрать искусственные взаимодействия **с UI сейчас**

- **Полностью убрать UI «Наши маленькие привычки»** и возможность вручную выбирать привычки/приветствия. Не создавать вместо этого новое меню привычек.
- **Убрать сценарии «Мне спокойно», «Побыть с Шанталь»**, их искусственные фразы вроде «Я пока осваиваюсь, можно просто посидеть рядом», «Посиди со мной немного», «Спасибо за компанию» и вызываемые ими повторяющиеся окна.
- **Не удалять историю, флаги, предпочтения, прогресс, черты, сохранения** в рамках данной задачи. Устаревшее поведение отключить на уровне UI и роутинга. Если реализация спрятана в другом модуле — найти её сначала.
- **Не заменять всё новой искусственной «болтовнёй».** Будущая система привычек возникает из игровых событий, истории, повторений и последствий решений. Разработку такой механики **отложить отдельным проектом** после стабилизации UI; сейчас только удалить ручной выбор и навязчивые псевдодиалоги.
- Не удалять без отдельного согласования полезные взаимодействия (например, поглаживание), получение наград, чтение рассказа, выбор реакции после завершённой истории.

### 1.6. Статистика

- **Отдельная нижняя вкладка.** Вверху **две маленькие метрики**, например серия дней и чистое время удержаний; названия, единицы и определения брать из существующих данных.
- Ниже календарь по месяцам, в каждой ячейке **цифра количества реально завершённых тренировок** за конкретную локальную дату. Продумать визуальные состояния 0, 1–9, двузначных значений, текущего дня, выбранной даты, дней с заморозкой.
- Под календарём видимый переход **«Журнал тренировок»** в отдельную страницу. Журнал — все сессии/типы, детали по нажатию, даты и статусы в понятном виде; не фильтровать молча важные записи.
- **Не показывать** одновременно отдельный недельный график и отдельную тепловую карту. Удалить их отображения из первичного UI, но не удалять исходные записи и вычисления.
- Другая аналитика (неделя к неделе, интенсивность, длительность/сложность, подробности дня) — в «Подробной статистике» или экране дня, не на главном экране вкладки.
- **Не менять** расчёт серий, семантику «чистого сжатия», поведение с `isDemo`, `isFreeMode`, замороженными датами и учёт часового пояса. Сохранять различие «полностью завершено»/«прервано».

### 1.7. Общие настройки

- Через шестерёнку: компактные строки **«Звук и вибрация»**, **«Оформление»**, **«Резервные копии»**, **«Дополнительно»**, при необходимости **«О приложении»**.
- Резервное копирование/восстановление доступно напрямую из списка настроек. Опасные операции — с подтверждением и понятным статусом, нельзя восстанавливать архив во время активной/приостановленной тренировки (действующее правило).
- Внутри «Звук и вибрация» сначала важные переключатели/громкость/выбранный профиль; развёрнутые звуковые профили, тесты нот и диагностику не показывать одновременно с основными настройками.
- Техническая диагностика — в «Дополнительно»/«О приложении», не в базовой ленте.
- Убрать постоянные длинные описания; `?` или `i` для действительно сложных параметров.

### 1.8. Настройки Шанталь (по отдельному снимку)

- Компактная группа **«Модель для историй»**: переключение Grok/Gemini; короткая строка безопасного статуса ключа; кнопка **«Проверить подключение»**.
- **«Управление ключом»** — дочерний экран/диалог: заменить, удалить (с явным подтверждением). Не показывать ключ целиком в UI и логах.
- **«Пробная история»** — под «Дополнительными настройками», с явным предупреждением, что API-вызов может быть платным. Не выполнять тест автоматически при открытии настроек.
- **«Изменения черт: показывать»** — один компактный переключатель с понятной подписью.
- Длинные технические рассказы о тарифе, передаче контекста и устройстве хранения ключа — по `i`, а не как постоянные абзацы. Не обещать бесплатность генерации и не подменять провайдера.
- **Не менять** сетевую интеграцию/провайдера, модель, настройки пользователя, хранение API-ключей или характеристики Шанталь ради визуального улучшения.
- Если данный экран отсутствует в checkout, зафиксировать это. Не сочинять альтернативную заглушку вместо реально используемой реализации.

## 2. Единая система UI и реакции на кнопки

### 2.1. Сетка и типографика

- Тёмная лесная палитра, кремовый текст, янтарный основной CTA; сохранить существующие темы/переключение тем, если это часть установленного приложения. Не раскрашивать каждую карточку отдельным акцентом.
- Рабочая сетка: 8 dp; внешние поля на компактном экране ориентировочно 16 dp; внутренние отступы 12–16 dp; интервалы между смысловыми секциями 16–24 dp. Это рекомендации, которые проверяются на реальных размерах, а не жёсткие пиксели.
- Не более одного визуально доминирующего CTA на экран; вторичные действия — спокойные `Outlined`/строки.
- Длинные названия/кнопки **не должны разрываться по одной букве**: вместо двух узких действий в строке использовать одну кнопку на всю ширину либо вертикальный стек, адаптивную сетку или перенос допустимых фраз. Не маскировать проблему микрошрифтом.
- Контент может прокручиваться; первичное действие и контекст должны быть доступны в начале. Не создавать несколько конфликтующих вложенных вертикальных прокруток.
- При увеличенном шрифте и узком телефоне компоненты должны **перекомпоновываться**; не устанавливать принудительный `fontScale = 0.92f` как универсальное решение переполнений. Использовать семантику доступности, проверять TalkBack, контраст, реальный порядок фокуса.
- Интерактивные зоны минимум **48 × 48 dp**; поддерживать системные insets, клавиатуру и жестовую навигацию.

### 2.2. Контракт реакций (обязателен для всех интерактивных элементов)

| Событие | Реакция |
|---|---|
| Коснулся интерактивного элемента | Видимый press/ripple/selected state; доступная метка. |
| Открыл предмет | **Сразу** модальная карточка по центру поверх текущей страницы, с коротким названием, описанием, свойствами и допустимыми действиями. Без скролла вниз к деталям. |
| Закрыл карточку | Возврат к той же позиции в сумке/магазине; выбор не теряет данные. |
| Купил/продал/использовал | Проверка предусловий; явное выполнение; один переход состояния; краткое подтверждение (Snackbar/статус); закрытие/обновление карточки. |
| Недостаточно монет/нет нужного ресурса | Объяснение рядом с действием, без молчаливого отсутствия реакции. |
| Действие может быть необратимым/дорогим | Подтверждение с предметом, ценой и результатом. Не требовать подтверждения для простого открытия карточки. |
| Проверка ИИ-подключения | Loading → success/error; без запроса к сети до явного нажатия. |
| Повторное быстрое нажатие | **Не дублировать** покупку, продажу, расходники, награды, начисление опыта. Заблокировать конкурирующие попытки на период операции, проверять состояние на уровне обработчика. |
| Системное «Назад» | Закрыть верхний диалог/подэкран, не сбрасывать активную сессию или позицию списка. |

Для **описания предмета/магазина** предпочтителен кастомный Compose `Dialog` с `Card` (центрированный); для длинного содержания разрешена прокрутка **внутри диалога** с ограничением по высоте, без выхода за экран. Простые результаты без выбора — короткий Snackbar или inline-статус. Действия **не должны каждый раз** вызывать навязчивый диалог.

### 2.3. Особо исправить: сумка, лавка, интерьер

**Текущее наблюдение в исходнике:** выбор `selectedBagItemId` выставляет состояние, а карточка `inventoryList.find { it.id == selectedBagItemId }` отображается ниже сетки предметов в `VelarisChantalScreen.kt` (ориентировочно строки 2007–2140). Это именно причина жалобы владельца.

**Требуемое изменение:**
1. Отделить список предметов от представления деталей; создать переиспользуемую `ItemDetailsDialog`/`ItemActionDialog` с типизированным выбранным ID.
2. По нажатию предмета менять `selectedItemId`, открывать `Dialog` поверх экрана **независимо от позиции списка**. При закрытии восстановить фокус и положение прокрутки.
3. Разные категории имеют разные разрешённые операции: изучить, подарить, заварить, экипировать, продать и т. п. **Сохранить реальные правила и цены**, не унифицировать всю игровую механику до одной кнопки.
4. Действия без подтверждённого результата не должны менять отображаемый баланс. После успеха использовать существующее состояние, не заводить второй независимый счётчик монет.
5. В магазине аналогично: нажатие товара → детали/цена/состояние покупки → подтверждение покупки → один результат. Для уже купленного товара показывать статус, не повторную покупку.
6. Карточки и длинные названия адаптивны на 320–360 dp и большом font scale; кнопка «Продать» **не может уходить в вертикальный столбик**.
7. Проверить «Алхимию у камина» и другие сложные действия: не удалять их; переносить на дочерний экран/доступное действие, если нужно для простоты.

## 5. Компактная стратегия тестирования — экономия токенов Codex

**Правило:** выполнение Gradle/тестов не требует генерации токенов само по себе; расход возникает, когда модель обрабатывает большие выводы, многократно пересматривает код и объясняет каждый из сотни успешных тестов.

| Когда | Что проверять | Что показывать Codex |
|---|---|---|
| После маленькой UI-правки | Компиляцию/проверки затронутого экрана, связанный UI-тест | Краткое резюме, коды выхода, только фрагменты ошибки |
| После работы со статистикой/сохранениями | Существующие тесты репозитория, Chantal persistence/backup; целевые новые тесты | `N pass / M fail`, при `fail` — нужные строки + путь к полному логу |
| После этапа навигации | Smoke для 4 вкладок, Back и активной тренировки | Короткий отчёт с матрицей |
| Перед готовым APK | Полный релевантный unit/Robolectric-набор и сборка | Сводка; полные логи в файле |
| При окончательной приёмке | APK поверх установленного, устройство, аудио при блокировке, экспорт/импорт | PASS/FAIL/NOT RUN, реальные значения |

- Запускать пакетно (например, штатными Gradle tasks), сохранять подробные логи в файлах; в чат выдавать **только необходимое**. Не спамить полными логами успешных 120 тестов.
- При ошибке сначала анализировать причину. Не пытаться бездумно повторять идентичную сборку.
- Не генерировать и не коммитить APK после каждой небольшой UI-правки. Собирать на контрольных рубежах и когда это действительно необходимо для проверки.
- Не удалять критически важные проверки ради экономии; сокращать только избыточные повторные прогоны и вывод.

### Сценарии регрессии, которые обязаны существовать

- Реальные занятия и сессии не пропадают; время удержаний/серии совпадают с исходным снимком; demo/free/plan не смешиваются.
- Календарь за один и несколько месяцев показывает реальные дневные количества; выбор даты и журнал согласованы.
- Активная тренировка продолжается при переходе на Шанталь/Статистику/Настройки и при блокировке экрана; stop требует подтверждения; пауза не увеличивает чистое время.
- Прогресс Шанталь после закрытия/возврата: монеты, энергия, инвентарь, черты, стадия, активный поход, невыданная награда, журнал.
- При двойном тапе по «Купить», «Продать», «Получить» операция происходит **не более одного раза**.
- Обновление APK поверх старой версии не сбрасывает Room, Preferences, состояние Шанталь и настройки модели/ключа.
- Резервный ZIP на **тестовом профиле** экспортируется, читается, восстанавливается без порчи данных; во время активного подхода восстановление блокируется.
- Сценарии отказа: повреждённый снимок Шанталь не перезаписывается пустым, недоступный API не вызывает самопроизвольных запросов/повторного списания денег, длинная карточка предмета не уходит за границы экрана.

## 6. Риски и решения

| Риск | Как исключить |
|---|---|
| Редизайн меняет исторические данные | Разделять read-only UI и репозитории, контрольный before/after snapshot, без миграций/очистки БД. |
| Навигация Шанталь создаёт повторную награду | Сохранять идентификаторы событий; тестировать повторное открытие/быстрый тап; не переносить наградную логику в recomposition. |
| Диалог теряет выбранный предмет после обновления | Хранить ID и проверять актуальность по коллекции; при исчезновении предмета корректно закрывать диалог. |
| Во время активной тренировки пропадают сигналы | Не менять ForegroundService/AudioFocus/WakeLock/timing, тестировать на устройстве. |
| После новой APK нельзя обновиться поверх | Сохранить package name/подпись, корректно увеличить versionCode при поставке; тестировать обновление, не uninstall. |
| Экран в APK не совпадает с GitHub | Остановить только затронутый этап, найти фактическую ветку/коммит; не писать фиктивную реализацию. |
| Слишком крупный рефакторинг и расход контекста | Малые стадии, маленькие PR/коммиты, краткий отчет, тесты по затронутым областям. |
| Масштабирование шрифта ломает кнопки | Адаптивные столбцы/перенос, large-font проверки, минимум 48dp touch. |
| API-ключи утекают в логи или backup | Не выводить и не копировать секреты; сохранить текущие политики хранения и маскировки. |

---

## 7. Формат отчёта Codex по каждому этапу

Только короткий отчёт, без стенограммы команд:

```text
Этап: <номер / название>
Исходный коммит / целевой коммит: <...>
Изменено: <до 8 пунктов; файлы/экраны>
Не менялось: Room / награды / статистика / таймер / ключи (указать исключения)
Тесты: <N PASS, M FAIL, K NOT RUN, ссылки на лог-файлы>
Проверка UI: <устройства/размеры или NOT RUN>
Известные ограничения: <...>
Следующий этап: <...>
```

**Не отмечать непроверенные функции как работоспособные.** Если UI-тест нельзя выполнить без устройства, это `NOT RUN`, а не `PASS`.

## 8. Стартовый промпт, который можно передать Codex

> Работай с моим Android-проектом Velaris по документу `VELARIS_UI_UX_MASTER_PLAN_CODEX_v2.md`. Это утверждённая продуктовая спецификация. Важнейшее: не потерять историю тренировок, статистику, прогресс Шанталь, предметы, награды, настройки API и работу таймера/звука при выключенном экране.\
> **Сейчас выполни только ЭТАП 0**: установи фактическую ветку/commit, сверь исходники с функциями на скриншотах, проверь структуру и точки хранения, предложи safe baseline/backup и составь компактную карту экранов. Не меняй игровую логику, БД, статистику и UI в этом запуске. Не делай push и не устанавливай APK без моего явного указания. Отчёт: короткий, с несоответствиями и приоритетом работ.\
> После моего отдельного разрешения переходи к ЭТАПУ 1. Выполняй каждый следующий этап отдельно, с целевыми тестами и сжатыми логами. Не запускай полную сборку APK после каждой мелкой правки.

### Контрольное «готово» для финального продукта

- [ ] Есть 4 вкладки и отдельные настройки через шестерёнку.
- [ ] Главная открывает основную тренировку без поиска кнопки и без многослойной статистики.
- [ ] Тренировки, таймер и результат компактны; остальные режимы доступны отдельно.
- [ ] Статистика содержит 2 метрики, месячный календарь с числом тренировок и отдельный журнал.
- [ ] Шанталь — крупная иллюстрация, живое состояние, один CTA, Сумка/История/Интерьер, «Мир Шанталь».
- [ ] Нет UI ручного выбора привычек и навязчивых «Побыть с Шанталь»/«Мне спокойно».
- [ ] Детали любого предмета/товара открываются **сразу** без прокрутки вниз.
- [ ] Кнопки не ломают текст, не допускают двойных наград/списаний и дают понятную реакцию.
- [ ] Общие настройки и настройки Шанталь компактны; API-ключи защищены, тест генерации только по запросу.
- [ ] Нет потери статистики, Room-данных, сюжетного состояния, денег/предметов и резервных копий.
- [ ] Физическое обновление APK и работа таймера с заблокированным экраном подтверждены либо честно помечены `NOT RUN`.
